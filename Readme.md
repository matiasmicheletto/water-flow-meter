# Water Flow Meter (ESP32-CAM + YF-S401)

A wireless water flow monitoring system based on the YF-S401 Hall-effect flow sensor and the AI-Thinker ESP32-CAM board.

The system measures water flow by detecting the pulses generated by the Hall-effect sensor as water passes through the meter. The ESP32-CAM processes these pulses, calculates flow measurements, and provides a web-based interface for monitoring the system and its recorded data.

The device is designed for deployment in open-field environments where Internet connectivity may not be available. The ESP32-CAM operates as a standalone Wi-Fi Access Point (AP) and hosts the application directly on the device. A captive portal automatically presents the application when a user connects to the device's Wi-Fi network, allowing the flow meter to be configured and monitored from a phone, tablet, or computer without requiring Internet access, external network infrastructure, or cloud services.

The hardware uses an LM2596 DC-DC buck converter to regulate the input supply to the 5 V required by the ESP32-CAM. The device supports a 12 V input, allowing it to be powered from a compact 12 V battery or a vehicle/car battery, making it suitable for autonomous deployment in remote locations where conventional power sources may not be available.

## Hardware

The YF-S401 output signal is fed through a voltage divider built with 10 kΩ and 18 kΩ resistors to reduce the sensor signal to a level much closer to the 3.3 V logic range required by the ESP32-CAM input. The board also includes a small supply stabilization network on the main VCC rail: a 470 µF electrolytic capacitor and a 150 nF ceramic capacitor placed near the board input to absorb current spikes caused by the Wi-Fi radio and keep the voltage stable during transmission bursts.

## Current firmware behavior

The firmware measures in fixed 1-second windows:

- `MEASUREMENT_INTERVAL_MS = 1000`
- `HISTORY_INTERVAL_MS = 1000`
- `FLUSH_INTERVAL_MS = 10000`
- `PULSES_PER_MINUTE_SCALE = 60000 / 1000 = 60`

Each sampling tick does the following:

1. Atomically read/reset the interrupt pulse counter.
2. Convert that 1-second pulse total into a flow rate:
   - `pulses_per_minute = pulse_count * 60`
3. Update cumulative `total_pulses`.
4. Store the sample in a RAM buffer and flush it to SD every 10 seconds.
5. Update the rolling live history used by the dashboard.

The CSV schema is still:

```csv
t_ms,pulse_count_10s,pulses_per_minute,total_pulses
```

The field name `pulse_count_10s` is retained for compatibility with the earlier version of the project, but in the current build it represents the pulses counted during the latest 1-second sample window.

Notes:

- Camera is intentionally not initialized so sensor/SD pin usage is preserved.
- Sensor input uses `INPUT_PULLUP` and interrupt on rising edge.
- If pulse noise causes overcounting, tune `MIN_PULSE_INTERVAL_US` in firmware.
- The AP is named `FlowMeter` with password `flowmeter123`.

## Interrupt-based pulse counting

- The ISR is intentionally minimal:
  - Reads `micros()`
  - Applies `MIN_PULSE_INTERVAL_US` debounce/noise filter
  - Increments a volatile pulse counter
- No heavy work, SD access, JSON generation, or serial writes happen in the ISR.

## SD logging and file handling

- A new log file is created every time the device boots, for example `/flow_log_0007.csv`.
- A persistent boot counter (`/boot_seq.txt`) tracks the next file index across reboots.
- Raw samples are buffered in RAM and flushed to SD every 10 seconds.
- `/api/files` lists all log files on SD, newest first, so the dashboard can offer a file picker.
- `/api/history` and `/api/export.csv` accept an optional `file` query parameter to inspect or export a previous session.
- The current session is served from the in-memory buffer and live-history state rather than re-reading the whole SD file on every poll.

## Dashboard behavior

The dashboard served from LittleFS provides three primary cards:

1. Current flow (`pulses/min`) from the latest completed 1-second sample.
2. Elapsed time since boot (`HH:MM:SS`).
3. Total pulses since boot, rendered with SI suffixes such as `k`, `M`, and `B`.

## API

### `GET /api/current`

Example:

```json
{
  "elapsed_ms": 123450,
  "pulse_count_10s": 15,
  "pulses_per_minute": 900,
  "total_pulses": 12345,
  "measurement_interval_ms": 1000,
  "has_measurement": true,
  "sd_ready": true,
  "current_file": "/flow_log_0007.csv"
}
```

### `GET /api/history`

The current implementation returns raw 1-second historical samples, not 10-second buckets.

Example:

```json
{
  "interval_ms": 1000,
  "measurement_interval_ms": 1000,
  "points": [
    { "t_ms": 1000, "pulses_per_minute": 60 },
    { "t_ms": 2000, "pulses_per_minute": 72 },
    { "t_ms": 3000, "pulses_per_minute": 84 }
  ]
}
```

This route accepts an optional `file` query parameter, for example:

```text
/api/history?file=/flow_log_0003.csv
```

When the current session is requested, the firmware uses a fast in-memory path. Historical files are replayed from SD when a previous log is selected.

### `GET /api/files`

Lists log files on SD, newest first:

```json
{
  "files": [
    { "name": "/flow_log_0007.csv", "current": true },
    { "name": "/flow_log_0006.csv", "current": false }
  ],
  "current": "/flow_log_0007.csv"
}
```

### `GET /api/export.csv`

Exports the full raw measurement history for the selected file or the current session.

```csv
t_ms,pulse_count_10s,pulses_per_minute,total_pulses
```

It accepts an optional `file` query parameter to export a specific log file instead of the active session.

## Running on hardware (PlatformIO)

Project config is `esp32cam` + Arduino framework + `115200` monitor/upload speed + LittleFS.

From the repository root:

1. Build firmware:

```bash
pio run
```

2. Upload firmware:

```bash
pio run --target upload --upload-port /dev/ttyUSB0
```

3. Upload the dashboard files to LittleFS:

```bash
pio run --target uploadfs --upload-port /dev/ttyUSB0
```

4. Open the serial monitor:

```bash
pio device monitor --port /dev/ttyUSB0 --baud 115200
```

5. If it is required to save output to a file use:

```bash
pio device monitor --port /dev/ttyUSB0 --baud 115200 --rts 0 --dtr 0 --filter esp32_exception_decoder --filter time --filter log2file
```

If upload fails, set the ESP32-CAM into flashing mode (IO0 to GND or hold the IO0 button as required by your adapter) and retry.

## Accessing the dashboard on device

- Connect to AP: `FlowMeter`
- Password: `flowmeter123`
- Open captive portal (or `http://10.0.0.1/`)

## Running the simulator

The simulator exposes the same API contract and serves the same dashboard UI.

From the repository root:

```bash
pip install -r requirements.txt
uvicorn simulator.main:app --reload
```

Open `http://127.0.0.1:8000/`.

Useful options:

- Start with long pre-generated history:

```bash
SIM_INITIAL_MINUTES=5000 uvicorn simulator.main:app --reload
```

- Reproducible randomness:

```bash
SIM_RANDOM_SEED=123 uvicorn simulator.main:app --reload
```

Simulation notes:

- Elapsed time continuously increases.
- Measurements are generated every 1 second.
- `pulses_per_minute` changes dynamically with noise and occasional shifts.
- The simulator exposes one synthetic log file (`/flow_log_sim.csv`) for API parity with the firmware.
- The dashboard and API behavior mirror the ESP32-CAM implementation closely, including file selection and CSV export.
